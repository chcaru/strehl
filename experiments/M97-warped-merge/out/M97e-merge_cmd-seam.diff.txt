FIVE THINGS TO CARRY WITH THE DIFF
-------------------------------------------------------------------------------

0. **`chunk_len` MUST BE >= 5 OR THE FEATURE IS SILENTLY INERT. THIS IS THE
   BIGGEST THING IN THIS FILE.**
   `z` needs a centred 5-frame window, so a chunk shorter than 5 never produces
   a centred frame and EVERY frame in it is elected with `z = 0`. The gate then
   does nothing at all, while reporting every frame elected, emitting no warning
   and producing a perfectly good photograph -- the shipped argmax.

   `merge_cmd` sets `chunk_len = frames.div_ceil(workers)` (:785) from a MEMORY
   budget, which knows nothing about this statistic. Measured on this rig:

       foam --limit 40   -> 13 workers, chunk_len 3 -> z scored 0 times
       109MSDCF --limit 22 -> 11 workers, chunk_len 2 -> z scored 0 times
       foam --limit 100  -> 13 workers, chunk_len 8 -> z scored 395,592,192 times

   The first two rendered byte-identically to HEAD and I very nearly reported
   that as "the gate is correctly quiet on a stationary stack". It was not
   quiet; it was disconnected. `FocusStats::window_starved_frames()` now counts
   exactly this, and ANY report of what the gate did must quote it. A healthy
   run shows `2 * Z_HALF * chunks`; a run where it equals `frames_folded` scored
   nothing.

   Whoever turns this on should floor `chunk_len` at `Z_WINDOW` when the feature
   is active, or refuse the run. I have not done it because `chunk_len` is
   computed in your file, not mine.

1. THE PASS-ONE MEMORY PLANNER AT :738 IS NOW WRONG WHEN THE FEATURE IS ON.
   The ring holds `Z_WINDOW` luma planes plus `Z_WINDOW` regularised planes,
   i.e. 10 * pixels * 4 bytes ~= 330 MB per worker at 3514x2344, on top of what
   the comment at :738 accounts for. With the feature OFF the ring is not
   allocated at all and the planner stays correct. Whoever turns this on at full
   resolution should either reduce `chunk_len` or reduce the ring: the
   regularised ring only needs depth `Z_HALF + 1`, not `Z_WINDOW`, which would
   take it to 8 planes. I have not made that optimisation because it is a
   change to code I would then have to re-control, and the feature is off.

2. `ctx.is_refused(index) { continue; }` AT :1726 PUTS A HOLE IN THE WINDOW.
   A refused frame is never folded, so the ring's five slots are the five
   *folded* frames, not five consecutive exposures. The window therefore spans a
   slightly wider focus baseline across a refusal. This is not wrong — the
   kernel annihilates any quadratic in the sample index however the samples are
   spaced in focus — but it is an approximation and it is worth knowing about.
   M86 recorded frame-level refusal as unit-test-only on real data.

3. `scratch.luma` IS THE WARPED LUMA, AND THAT IS REQUIRED, NOT INCIDENTAL.
   `field_for` warps the frame in place at :968 before computing luma. If `z`
   were computed on unregistered luma, focus breathing alone (232.7 px on
   `bee-3-cpl`, fact from M86) would make every frame disagree with every other
   and the gate would reject the entire stack. On an unregistered stack the
   graceful outcome is that every frame goes ineligible and the election falls
   back to the shipped argmax — `FocusStats::robust_fallbacks()` counts exactly
   that, and a large number there means the gate did nothing and should be
   reported beside any claim that it did something.

4. DEFAULT IS `Arm::Soft` AND `Arm::Hard` MUST NOT BECOME THE DEFAULT.
   `on`/`1`/`true`/`soft` all select Soft. This is measured, not preferred:
   `merge::tests::trap_soft_keeps_the_only_frame_that_resolves_the_pixel`
   constructs a frame that disagrees at 6 sigma *because it is the only frame
   that resolves the pixel*, and asserts that Soft keeps it while Hard discards
   it on identical evidence.

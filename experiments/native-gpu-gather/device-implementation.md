# Device coordinate implementation (source only)

The explicit `STREHL_GPU_SCHEDULE=device` schedule writes the same 16-byte `SamplePlan` records directly into the existing 256-row device strip. Three binary f64 transforms (96 bytes) are uploaded once per frame. Geometry uses the original full-plane centre, the current complex multiply/add order, support admission in f64, clamp/floor in f64, and only then f32 fractions. The existing image WGSL and strict f32 SPIR-V compiler are unchanged. GPU selection remains off by default; its ordinary schedule remains Parallel256. Serial32 and Parallel256 construction do not require f64 hardware.

`src/coordinates.glsl` is an embedded, owned coordinate kernel. `src/device-coordinates.rs` requires a discrete Vulkan adapter with Vulkan 1.2, SHADER_F64 and PASSTHROUGH_SHADERS, f64 signed-zero/Inf/NaN and denorm preservation, and RTE32/RTE64 properties. Denorm independence NONE is refused. It requests Preserve64 and RTE32/64 execution modes plus NoContraction on all generated floating arithmetic results. Accepted nonzero coordinate fractions are at least 2^-52, so the final f32 conversion cannot create a subnormal; there is no other nontrivial f32 coordinate arithmetic. All non-dyadic coefficients arrive in the f64 storage buffer, avoiding Naga's unsupported GLSL double-literal syntax.

The original Naga module and original generated SPIR-V are fully parsed/IR-validated. The final fixed capabilities, extension, execution modes and arithmetic decorations are structurally checked; removing exactly those additions must recover the original words. Naga cannot import the new execution modes, so the patched module is **not fully Naga-validated and is not spirv-val certified**. The private unsafe handoff accepts only this embedded module. This limitation and original/submitted hashes are in the serialized coordinate report. Required float-control semantics are from the [Vulkan SPIR-V environment](https://docs.vulkan.org/spec/latest/appendices/spirvenv.html) and [SPIR-V specification](https://registry.khronos.org/SPIR-V/specs/unified1/SPIRV.html).

The actual geometry pass precedes the unchanged gather pass in one encoder, using the same descriptor buffer. Ordinary Device256 calls have no descriptor readback/upload or CPU descriptor vector. The existing independent mutator seam explicitly reads device-generated plans back, mutates them and uploads the altered strip; that control cost is separately included in transfer counters. `device_plans_for_test` dispatches this same geometry pipeline directly. It refuses zero/odd extents, oversized/end-overflow strips, index overflow and device dispatch/buffer limit violations. A host-only GPU context cannot silently switch to Device256; consumption returns an error.

Detailed on-logging serializes hardware and compilation reports; off/placebo retain their established behavior. Every successful Device256 consumer call adds an unconditional completion marker based on its returned schedule. No build, shader compilation, GPU invocation, image run, numerical result, hardware-support claim or speed claim was produced by the author. Root owns the fixed descriptor controls, unchanged 18 actual-image cases and any later complete-render timing decision.

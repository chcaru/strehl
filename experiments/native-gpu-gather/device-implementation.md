# Device coordinate implementation (source only)

The explicit `STREHL_GPU_SCHEDULE=device` schedule writes the same 16-byte `SamplePlan` records directly into the existing 256-row device strip. Three binary f64 transforms (96 bytes) are uploaded once per frame. Geometry uses the original full-plane centre, the current complex multiply/add order, support admission in f64, clamp/floor in f64, and only then f32 fractions. The existing image WGSL and strict f32 SPIR-V compiler are unchanged. GPU selection remains off by default; its ordinary schedule remains Parallel256. Serial32 and Parallel256 construction do not require f64 hardware.

`src/coordinates.glsl` is an embedded, owned coordinate kernel. `src/device-coordinates.rs` requires a discrete Vulkan adapter with Vulkan 1.2, SHADER_F64 and PASSTHROUGH_SHADERS, f64 signed-zero/Inf/NaN preservation and RTE32/RTE64 properties. It requests those execution modes plus NoContraction on all generated floating arithmetic results. All non-dyadic coefficients arrive in the f64 storage buffer, avoiding Naga's unsupported GLSL double-literal syntax.

The first root invocation refused before GLSL/descriptor/image work because this adapter reports no f64 denorm preservation; its result is preserved in commit `c6e7a152023a9d83fd89687aaa2586fe65877e44`. The subsequent source-only adaptation removes the DenormPreserve capability/mode and applies an independently reviewed guard to **all twelve precomposed coefficients**, including R/B during green-only calls. Zero and nonfinite coefficients are allowed; every finite nonzero coefficient must have absolute value at least 2^-900. Hardware denorm support remains visible in the report. No coefficient is rounded or changed by the guard.

Proof for this exact expression: admitted finite coefficients are multiples of 2^-952. Pixel/centre differences are exact half-integers under the existing dimension/index bounds. Products therefore lie on a 2^-953 lattice; finite additions, subtractions, RTE rounding and the final multiplication by two preserve it. Every finite nonzero intermediate is at least 2^-953, above binary64 normal-minimum 2^-1022. Overflow may produce Inf/NaN and remains covered by SINF64 plus the existing invalid admission. After support admission, any nonzero floor fraction is at least 2^-52 and is normal in f32. No denorm mode is needed on this guarded device path.

An unsafe actual frame uses the unchanged Parallel256 CPU coordinate planner while retaining the strict GPU image arithmetic. Its returned schedule is Parallel256, with a nonempty `coordinate_fallback` reason and an unconditional fallback marker; no Device256 completion marker is emitted. This preserves the full original input contract and prevents a fallback being counted as successful device-coordinate timing. The direct descriptor helper refuses unsafe coefficients instead.

Naga 30.0.1 `back/spv/writer.rs:3707` emits `SPV_KHR_storage_buffer_storage_class` whenever the target version is below 1.3 and the module has storage buffers. The owned coordinate module uses target 1.0, so the adapter now requires exactly one canonical, correctly placed instruction with that name and records it in `original_extensions`. Unknown, duplicate, malformed or misplaced original extensions still refuse. The original extension is preserved byte-for-byte; the separate `SPV_KHR_float_controls` addition follows the original extension block. This compiler-interface repair changes no shader arithmetic or fixture.

The original Naga module and original generated SPIR-V are fully parsed/IR-validated. The final fixed capabilities, extension, execution modes and arithmetic decorations are structurally checked; removing exactly those additions must recover the original words. Naga cannot import the new execution modes, so the patched module is **not fully Naga-validated and is not spirv-val certified**. The private unsafe handoff accepts only this embedded module. This limitation and original/submitted hashes are in the serialized coordinate report. Required float-control semantics are from the [Vulkan SPIR-V environment](https://docs.vulkan.org/spec/latest/appendices/spirvenv.html) and [SPIR-V specification](https://registry.khronos.org/SPIR-V/specs/unified1/SPIRV.html).

The actual geometry pass precedes the unchanged gather pass in one encoder, using the same descriptor buffer. Ordinary Device256 calls have no descriptor readback/upload or CPU descriptor vector. The existing independent mutator seam explicitly reads device-generated plans back, mutates them and uploads the altered strip; that control cost is separately included in transfer counters. `device_plans_for_test` dispatches this same geometry pipeline directly. It refuses zero/odd extents, oversized/end-overflow strips, index overflow and device dispatch/buffer limit violations. A host-only GPU context cannot execute device coordinates: an eligible Device256 request returns an error if that pipeline was not constructed. Unsafe coefficients select the explicit Parallel256 input-domain fallback.

Detailed on-logging serializes hardware and compilation reports; off/placebo retain their established behavior. Every successful Device256 consumer call adds an unconditional completion marker based on its returned schedule. No build, shader compilation, GPU invocation, image run, numerical result, hardware-support claim or speed claim was produced by the author. Root owns the fixed descriptor controls, unchanged 18 actual-image cases and any later complete-render timing decision.

# GPU-resident fold and a CPU/GPU/RAM planner

**Status:** Stages 1-2 BUILT (GPU fold, CPU-side weights replaced by portable `ln`/`exp`
after the owner approved a one-time change); stage 3's GPU preparation and one-deep
probe/fold overlap BUILT; the planner is only its first rule (decoder threads).
**Date:** 2026-11-08.
**Scope:** the default `stack --merge pyramid` path, desktop and CLI.

## Where the time goes now

MEASURED on bug-7 (33 MP, Ryzen 9 9950X3D, 64 GB, RTX 5090), after the
streaming/banded work of 2026-11-08 and the fold fusion that followed it:

| Stage (per frame, 32 threads, look-ahead 1) | Wall |
| --- | ---: |
| `pyramid-add` (the fold; serial in frame order) | 77 ms |
| gate-floor probe | 78 ms |
| full-resolution gather (banded) | 60 ms |
| plane extraction and luma | 13 ms |

Pipelined, a 100-frame render runs at 0.20 s per frame. The fold is
memory-bandwidth bound: it scaled 0.26 / 0.22 / 0.23 s per frame at
8 / 16 / 32 threads, and each frame moves roughly 5 GB of pyramid and
accumulator data. A CPU cannot move that much faster; an RTX 5090 has about 25x
the memory bandwidth and 32 GB to keep every accumulator resident.

The existing GPU gather (`native-gpu-gather`, Vulkan, strict SPIR-V) is
bit-identical but no longer faster: 0.25 s per frame against the banded CPU
gather's 0.22 on the same 100 frames, pixel-identical. It uploads a frame,
computes, and downloads it synchronously under one lock. Offloading gather alone
leaves the bandwidth-bound fold where it was.

## Exactness on this device

The project's contract is pixel identity with the CPU. The fold needs more than
multiply/add. Probe: `experiments/native-gpu-gather/src/arith-probe.rs`, run via
`cargo test --release -p strehl-cli --features native-gpu-gather --lib --
--ignored gpu_arith_probe libm_rounding_census --nocapture`.

MEASURED, 4 x 2^24 operand pairs (half in the fold's 1e-3..1e9 range, half over
random finite normal bit patterns), NoContraction SPIR-V, RTX 5090, driver 621.01:

| GPU operation | Mismatches against the CPU |
| --- | ---: |
| f32 `x / y` | ~29% (1 ulp) |
| f32 `sqrt` | ~17% |
| `f32(f64(x) / f64(y))` | 0 |
| `f32(sqrt(f64(x)))` | 0 |
| f64 `x / y` | 0 |
| `x * y + x`, `max`, `min` | 0 |

So every f32 division and square root must be evaluated through f64 and rounded
(exact by the 2p+2 theorem when f64 is correctly rounded, which this device's f64
was on every sample). f64 runs at 1/64 rate on this part; the fold's ~50 M
divisions per frame cost about a millisecond.

`ln` and `exp` are the hard part. MEASURED exhaustively on the CPU: the
platform's f32 `ln` differs from the correctly rounded value on 210,365 of the
2,130,706,432 positive normal inputs, and `exp` on 23,093 of 2,235,564,034
inputs in [-80, 80]. They are not correctly rounded, so no independent GPU
implementation can be assumed to match them. Two exact routes:

1. **CPU weights.** The GPU computes the selection ratio `r` exactly (it is all
   divisions and multiplies); the CPU evaluates `exp(clamp(p ln r))`; the GPU
   receives `w`. About 88 MB per frame across PCIe and ~5 ms of CPU time.
2. **Exception tables.** A GPU `ln`/`exp` (f64 evaluation, rounded) plus a table
   of the inputs where it disagrees with the CPU's function, generated by running
   both over **every** f32 input in the domain (seconds on this machine) and
   keyed to the C runtime's identity. Exact for all inputs by construction, a few
   hundred thousand entries.

Note what the census also shows: the CPU path is itself only bit-reproducible for
a given C runtime. That is true today and not introduced by this proposal.

## Proposed architecture

**Per frame on the GPU**, frames streamed, accumulators resident:

1. Upload the decoded u16 CFA (66 MB at 33 MP; ~3 ms on PCIe 5).
2. Mosaic, Malvar, Catmull-Rom gather and quantise: the existing exact kernels,
   moved to row bands written straight to quad planes, with device coordinates.
3. Probe: the CPU fills the seeded noise field (it uses the C runtime's
   `ln/sin/cos`); the GPU gathers it with the same kernels. The interior
   mean-square sums are sequential f64 on the CPU and stay there (download levels
   0-3 interiors, ~40 MB), unless proven exact in another order.
4. Luma, variance (`sqrt` through f64), the luma Laplacian and variance Gaussian
   pyramids, band energy, pooled evidence, ratio `r`: all multiply/add/divide.
5. Weights by route 1 or 2 above.
6. Accumulate `num`, `usum`, `den`, the ensemble sums and the hull in VRAM.

**Once per render on the CPU:** ensemble thresholds (quantiles), collapse, writer.

The canonical chunk partition is unchanged: a chunk's accumulator is a VRAM
allocation, absorbed in the same order. Reduction order inside the fold is
per-coefficient, not cross-coefficient, so no parallel reduction changes a bit.

**Expected.** Per-frame GPU work ~10-20 ms, bounded by the CPU's own stages
(decode ~45 ms single-threaded, already ahead on 4 threads; probe noise fill)
and PCIe. Roughly 1,444 frames in one to two minutes instead of ~5. DERIVED, not
measured.

## The planner

One component decides resources; nothing else hard-codes them. It reads host RAM,
logical cores, GPU presence/VRAM/link width, and the frame geometry, and sets:

- alignment window (`LADDER_WINDOW_BYTES`), decode-ahead window and decoder
  threads, look-ahead slots, execution threads;
- which stages run on the GPU, and the CPU/GPU overlap: the GPU prepares and
  folds frame *n* while the CPU decodes frame *n + k*, fills its probe noise, and
  evaluates frame *n - 1*'s weights;
- VRAM residency: accumulators plus a ring of in-flight frames.

It must **never** influence arithmetic grouping: canonical chunks stay derived
from geometry and the fixed `MEMORY_BUDGET_BYTES`, as now. The planner's choices
are printed in the run banner and recorded with the output, like the worker count
today, and a placebo/CPU-only switch reproduces the identical pixels.

## Staging and gates

1. Exact kernels: division/sqrt through f64 helpers; pyramid reduce/expand and
   the fused level sweep in strict SPIR-V. Gate: bit-identity against the CPU
   functions on random and real levels.
2. GPU fold behind a feature and switch, CPU weights (route 1). Gate: decoded
   pixels and linear master identical on bug-4 and bug-7; byte-freeze suite.
3. Planner and asynchronous overlap. Gate: same pixels at every planner choice;
   measured wall time and peak RAM/VRAM against the CPU path, same binary,
   alternating arms (`docs/agents/engineering-ledger.md` rule 50).
4. Optional: exception-table transcendentals (route 2), if route 1's PCIe or CPU
   cost measures as the limit.

## Decisions for the owner

- **Pixel identity, or a one-time rebaseline?** If the project accepts a single,
  deliberate change of the CPU's `ln`/`exp` to a portable, correctly rounded
  implementation shared by CPU and GPU, route 2's tables disappear and outputs
  stop depending on the C runtime. Differences would be ±1 DN in rare
  coefficients. Proposed default: keep pixel identity (route 1) until measured.
- **Prepared-frame cache.** Re-rendering one stack with new settings repeats
  decode, gather and probe. A disk cache of each frame's prepared planes would
  remove that, but it is an aligned-frame volume, which `AGENTS.md` forbids. Not
  proposed without an explicit decision to amend that invariant.

## Outcome, 2026-11-08

The owner accepted a one-time, near-imperceptible output change, so route 2's tables were
not needed: the CPU and GPU now share `strehl_core::portable_math` for the weight's
`ln`/`exp` (bug-7, 300 frames: 2,526 of 98.9 M samples moved by exactly 1 DN; byte-freeze
rows re-baselined with the attribution recorded). `crates/strehl-gpu` implements the fold
(stage 2); `STREHL_GPU_FOLD=on|auto|off`.

A fourth exactness condition was found end to end, not in the synthetic test: the device
flushed f32 subnormals, and the soft-power numerator is subnormal wherever every frame's
weight sits at the `exp(-80)` clamp. `DenormPreserve` on every entry point fixed it; the
synthetic test now includes a noisy flat region that fails without it.

MEASURED, desktop path (sRGB + linear master + UI progress + CA preview), RTX 5090:

| bug-7 | CPU fold | GPU fold | pixels |
| --- | ---: | ---: | --- |
| 300 frames | 69.4 s | 45.3 s | identical (photograph and float master) |
| 1,444 frames, alignment cached | 329.9 s (645.2 s at `86cdc47ec`) | 209.2 s | identical (photograph and float master) |

With the fold on the GPU the per-frame cost is now the CPU's frame preparation (gather,
probe, extraction): ~0.12 s per frame. Stage 3 (GPU preparation, planner and overlap) is the
next lever; the gather kernels already exist and are exact.

### Stage 3, GPU preparation (2026-11-08)

Built as described in `docs/ARCHITECTURE.md` § The GPU fold. What changed from the plan
above, and why:

- **The probe noise moved to the device, not stayed on the CPU.** A portable f64 `ln` and
  `sin`/`cos` reproduce the C runtime's quantised noise exactly on 2^30 samples, so the CPU
  switched to them and the 66 MB probe frame is no longer built, filled or uploaded.
- **The pooled sums moved too**, by fixing their association (rows, then rows of row sums)
  instead of keeping one sequential sum. This was not on the plan: it was the price of the
  44 MB probe download plus a 5 ms serial sum per frame.
- **f64 throughput, not exactness, was the device limit.** The noise kernel was 5.3 ms per
  frame in f64; an f32 screen with an exhaustively bounded error and an f64 fallback near
  rounding boundaries made it 1.0 ms without changing a sample.

MEASURED progression on bug-7, CLI `stack --merge pyramid --srgb --refine-ca=off`, fold
wall from the `folded` line (four canonical chunks either way, each end ~0.2 s):

| Step | 100 frames | 200 frames |
| --- | ---: | ---: |
| CPU preparation (GPU fold) | 20.6 s | |
| device gather/probe, CPU-filled probe uploaded | 5.9 s | |
| device probe noise, probe levels read straight into the CPU pyramid, null after submit | 4.8 s | |
| frames freed on decoder threads | | 7.1 s |
| ensemble null's levels in parallel | | 6.3-6.4 s |
| device interior sums and null windows (no pyramid download) | | 5.5-5.6 s |

### Stage 3, data movement (2026-11-08)

The four items that were listed as remaining here, all built, none changing an operation's
inputs or order (`docs/ARCHITECTURE.md` § The GPU fold, *Data movement*):

- **Overlap.** A third raw slot; frame *n + 1* is decoded, staged and probed before frame *n*
  waits for its own probe (`probe_submit`/`probe_collect`, a wait on that submission only).
  It showed no clear gain until the CPU's ensemble-null work left the critical path.
- **The ensemble null on the device.** The CPU null took a median 4 ms per frame, often over
  20 ms; the device accumulates it next to the probe and the CPU only counts frames and
  hands back each band's unit. The per-frame download is the 32-byte sums.
- **A persistent mapped upload ring** (two buffers, re-mapped after each device copy).
- **Chunked chunk-end readback** through one 64 MB buffer: peak private memory ~8.1 to
  ~7.1 GB at 200 frames.
- **mimalloc** as the engine's allocator, not on the plan: decoding, not the device, was the
  limit, and large-block page faults contended across 8 decoders (one decode 125 to 88 ms).
  A hand-written cache of freed large blocks was tried first and gave nothing measurable.

MEASURED, full stack, desktop path, CLI `stack --merge pyramid --srgb --linear-master`,
`STREHL_UI_PROGRESS=1 STREHL_GPU_FOLD=on`, alignment cached, `--features temporal-energy,gpu`
release builds of `865777ad8` and of this change alternated (ABBA), otherwise idle machine:

### Stage 3, decoding (2026-11-08)

Instrumenting the fold loop showed it waiting on decodes ~5.6 ms per frame, and more decoder
threads did not help: the linked decoder parallelises inside each file on the shared pool,
~165 ms of CPU per frame, and decoding alone stopped at ~78 frames/s on 32 logical cores
(MEASURED). Sony's lossless raw is tiled lossless JPEG, so `strehl_raw` now decodes those
pixels itself from ITU-T T.81 (`docs/ARCHITECTURE.md` § The GPU fold, *Decoding*), checked
sample-for-sample against the linked decoder on 4,052 files. The steps, one thread, per frame
of tile decoding: a first table-per-sample version 90 ms; registers instead of memory for the
reader state (a macro per interleave width) ~80 ms; a 13-bit table giving the finished
difference 52-56 ms; refilling without a branch, two tiles per loop 49 ms. Then the pipeline:

- one file per thread means the thread count is the parallelism: 8 decoders left the fold
  waiting, 16 did not (`decode_ahead::decoders`, half the logical cores);
- with 16 decoders, freed 73 MB buffers were decommitted and faulted in again; handing each
  staged frame's buffer to the next decode (`strehl_raw::decode_into`) gave the speed of
  disabling mimalloc's purge with 1 GB less peak memory.

MEASURED, same command and alternation as above, against `b3bf9da00`: 26.5 / 26.7 s against
33.1 / 33.5 s; fold 17.2 / 17.4 s against 23.5 / 23.9 s; CPU time 300 / 309 s against 579 /
578 s; peak private 9.40 / 9.22 GB against 7.38 / 7.32 GB. Photograph and float master
identical to the CPU path's. CPU fold path at 200 frames: unchanged within noise (alignment
11.1 to 10.6 s, fold 41.3 to 40.6 s).

### Stage 3, host memory (2026-11-08)

A private-memory timeline of the full run (sampled every 250 ms) put the peak inside the main
fold, 8.0-9.0 GB throughout, not at collapse and output (6.2 GB); peak working set was only
5.9 GB, so ~3 GB was committed and never touched. The GPU path still allocated what it no
longer used, and from the second chunk held two host merges of ~0.84 GB each:

- the worker's `BandMerge` totals: a GPU chunk's totals are on the device, and the host copy
  was only a readback target before `absorb`. Now the first chunk is read into the retained
  merge and later chunks are absorbed into it as they are read (`GpuFold::absorb_chunk`),
  with `absorb`'s own elementwise operations (`BandMerge::EXTERNAL_ABSORB`); the worker's
  merge releases its totals and only counts frames, plus the ensemble null's windows when the
  host accumulates them (`absorb_external_remainder`). A core test checks the table against
  `absorb` bit for bit with signed zeros and infinities among the values, for windows held by
  the device or the host and for first and later chunks, and fails when one entry is swapped
  or host windows are skipped; a device test absorbs three chunks against the CPU's chunked
  `absorb`, collapsed output included.
- Caught by running the other route: the first version moved only the null windows' frame
  counts. With preparation on the CPU (`STREHL_GPU_PREP=off`) the windows are accumulated on
  the host, not the device, so they were dropped and 5.1% of photograph samples changed (up
  to 1,578 DN). The byte-freeze rows run the CPU fold and could not see it; the core test
  passed because it described host windows as `[false; n]` where the device reports an empty
  list. Both are fixed, and the planted omission now fails the test.
- the CPU fold's `FrameWorkspace` (~0.9 GB), and under GPU preparation the CPU's warp scratch,
  planes, luma and variance (~0.3 GB).

MEASURED, same command as above, against `307700079`, alternated (ABAB): 25.9 / 26.0 s
against 27.0 / 27.0 s; peak private 7.11 / 7.11 GB against 8.90 / 8.86 GB; peak working set
3.85 / 3.84 GB against 5.86 / 5.79 GB. With CPU preparation (one run each): 208.7 s
against 208.9 s, peak private 8.28 GB against 9.91 GB, working set 5.94 GB against 7.47 GB.
Photograph and float master identical to the CPU path's on both routes (final build); byte-freeze
rows unchanged. The fold's private memory is now ~6.5 GB over a ~2.2 GB
base between passes: the retained merge, the decode window (up to 18 frames of 73 MB) and the
device's host-side buffers.

Remaining: the fold waits on the device (~12 ms per frame: upload, probe and fold kernels),
which is where fusion of the probe's passes would pay; a decode window sized from measured
decode and fold rates rather than the thread count; the desktop's live views on the GPU path.
